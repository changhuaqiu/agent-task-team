# 业务规范

本规范适用于需求理解、业务分析、产品抽象、UX 决策、角色体系、协作机制、文案和业务评审动作。

## 1. 业务动作前置检查

开始业务动作前必须完成：

- 阅读 `docs/README.md`，确认产品、业务、UX、技术文档的归属位置。
- 查找并阅读相关 `docs/product/`、`docs/wiki/`、`specs/<name>/` 和已有设计资料。
- 如果用户要求参考现有产品或已有实现，必须先查看真实实现或真实页面，不从记忆虚构。
- 明确目标用户、使用场景、成功标准和非目标。

## 2. 产品判断原则

业务与产品方案必须满足：

- **用户语言优先**：面向用户的概念使用用户能理解的语言，不暴露 runtime、bridge、routing、providerHints 等内部实现词。
- **主任务清晰**：一个页面或流程应有一个主动作；不要把所有可能性平铺给用户。
- **对象模型稳定**：账号、团队、角色、任务、会话、协作、审查等核心对象必须定义清楚，避免同一对象多套叫法。
- **协作可解释**：多 agent 协作必须能回答谁负责、谁持有上下文、谁能唤醒谁、失败如何反馈。
- **渐进披露**：高级配置、诊断信息和内部状态应放在次级入口，不干扰主要流程。
- **少即是多**：当用户反馈“乱、散、重复、不像参考”时，先重构信息架构，不继续堆组件。

## 3. 业务分析输出规范

业务分析必须输出：

- 当前问题或机会的清晰定义。
- 目标用户和核心场景。
- 业务对象及其关系。
- 成功标准与不做范围。
- 对技术实现的约束，而不是直接替技术层拍脑袋。
- 需要沉淀到产品文档、规格或决策记录的结论。

## 4. UX 与文案规范

涉及 UX 或文案时必须遵守：

- 页面主体展示用户当前已经拥有或正在处理的对象。
- 创建入口只询问当前步骤必要字段。
- 认证、账号、模型配置等流程按用户选择动态展示字段。
- 同一选择不在页面主体和弹窗中重复询问。
- 错误文案说明用户可执行的下一步，不只展示内部错误。
- 诊断信息可以存在，但默认不压过主流程。

## 5. 业务决策规范

出现以下情况必须更新 `docs/product/` 或 `docs/wiki/`：

- 引入新的核心业务对象或改变对象关系。
- 改变用户流程、页面信息架构或协作机制。
- 改变角色职责、权限、任务分配或审查门禁。
- 将一次性讨论沉淀为后续迭代必须遵守的产品原则。

业务决策至少包含：用户问题、业务目标、采用方案、放弃方案、对技术和 UX 的约束。

## 6. 业务交付检查清单

交付前逐项检查：

- [ ] 已区分用户概念与内部实现概念。
- [ ] 已明确主任务、核心对象和不做范围。
- [ ] 已检查是否与现有产品文档或规格冲突。
- [ ] 已同步相关产品、UX 或业务文档。
- [ ] 已判断是否有可沉淀业务知识。
