# 迭代知识沉淀规范

本规范定义每轮迭代结束时如何识别、分类和沉淀知识。目标不是增加文档负担，而是避免关键经验只留在聊天记录里。

## 1. 每轮结束必须回答的问题

每轮迭代结束前，必须显式判断：

1. 本轮是否改变了系统事实、业务规则、用户流程或协作机制？
2. 本轮是否发现了会再次踩坑的问题、约束或经验？
3. 本轮是否形成了未来必须遵守的原则、命名、边界或流程？
4. 本轮是否废弃、替代或修正了已有方案？
5. 本轮是否有无法完成但必须追踪的后续事项？

只要任一答案为“是”，就需要沉淀。

## 2. 知识分类与落位

| 知识类型 | 落位 | 示例 |
| --- | --- | --- |
| 当前实现事实 | `docs/wiki/` | 模块职责、数据流、运行方式、已落地行为 |
| 长期技术设计 | `docs/technical/` 或 `architecture/` | 执行链路、控制面、存储模型、集成协议 |
| 产品/业务原则 | `docs/product/` | 用户模型、业务对象、角色协作规则 |
| 架构/产品决策 | `decisions/` | 事实源迁移、协作模型取舍、重大替代方案 |
| 活动实现契约 | `specs/<name>/` | 正在执行的功能规格、任务、验收清单 |
| 可复用经验 | `docs/knowledge/` | lessons learned、排障经验、反模式 |
| 已失效资料 | `docs/archive/` | 被替代但仍有历史参考价值的计划或规格 |

进入 `docs/knowledge/` 的内容还必须按 `docs/standards/knowledge-governance.md` 标注知识层级、类型、成熟度、证据和权威位置，并同步更新 `docs/knowledge/catalog.md`。

## 3. 沉淀粒度

沉淀应遵守：

- 优先更新已有文档，不为每个小结论创建新文档。
- 一个结论只保留一个权威位置，其他地方用链接或索引引用。
- 事实型文档必须写清“当前已实现”和“目标状态”的区别。
- 临时 workaround 必须写明退出条件。
- 不把聊天过程原样搬进文档，只保留可复用结论。

## 4. 迭代收尾流程

每轮完成前执行：

1. 对照本规范第 1 节识别可沉淀知识。
2. 按第 2 节选择落位。
3. 如果落位是 `docs/knowledge/`，先查 `docs/knowledge/catalog.md`，优先更新已有条目；新增条目必须使用 `docs/knowledge/templates/knowledge-entry.md` 的字段。
4. 更新相关文档或明确说明“本轮无新增可沉淀知识”。
5. 若有后续事项，写入对应 `tasks.md`、计划文档或 issue，而不是只写在最终回复里。
6. 最终交付中说明更新了哪些规范、规格或知识文档。

## 5. 最终交付必须包含的沉淀判断

最终交付说明中必须包含一个简短判断：

- **已沉淀**：列出更新的文档路径和沉淀内容。
- **无需沉淀**：说明原因，例如“纯格式调整，未改变项目规则或事实”。
- **待沉淀**：只有在当前轮无法安全落文档时使用，并必须说明阻塞原因和建议落位。
- **引用知识**：如果本轮使用了 `docs/knowledge/` 中的知识，列出被引用的条目 ID 或文档路径。

推荐格式：

```text
知识沉淀：
- 已沉淀：docs/wiki/04-backend-daemon.md，补充 runtime health 当前实现事实。
- 无需沉淀：本轮测试命令输出无长期复用价值。
- 待沉淀：无。
- 引用知识：KG-001。
```

## 6. 不需要沉淀的情况

以下情况通常不需要新增长期知识：

- 纯格式调整且不改变规则。
- 一次性解释，没有形成项目约束。
- 临时命令输出，没有复用价值。
- 与项目无关的外部事实。

即使不需要沉淀，也应在交付前确认相关文档没有被代码行为改变。
