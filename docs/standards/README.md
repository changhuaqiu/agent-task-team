# 项目规范入口

本目录是项目协作规范的正式入口。所有开发动作、业务分析动作、需求拆解、方案设计、评审与交付总结，都必须先对齐这里的规范。

## 规范分层

| 层级 | 文档 | 适用动作 | 核心问题 |
| --- | --- | --- | --- |
| 技术规范 | `docs/standards/technical.md` | 代码实现、架构设计、数据模型、接口、测试、运行时与集成变更 | 这个改动是否稳定、可验证、可维护 |
| Git / Worktree 规范 | `docs/standards/git-worktree.md` | 分支、工作树、暂存、提交、并行开发与清理 | 改动是否隔离、可追溯、不会丢失 |
| 业务规范 | `docs/standards/business.md` | 需求分析、产品抽象、UX 决策、角色/协作机制、业务文案 | 这个判断是否符合用户价值和产品模型 |
| 迭代沉淀 | `docs/standards/iteration-knowledge.md` | 每轮迭代收尾、复盘、文档更新、知识归档 | 哪些知识应该沉淀为长期资产 |
| 知识治理 | `docs/standards/knowledge-governance.md` | 知识入库、索引、成熟度、引用和淘汰 | 知识是否能成为可复用资产 |

## 强制执行顺序

每一轮工作必须按以下顺序执行：

1. **识别动作类型**：判断当前是技术开发、业务分析，还是混合任务。
2. **读取对应规范**：技术任务读技术规范；业务任务读业务规范；混合任务两者都读。
3. **检查 Git / Worktree 边界**：所有会产生仓库变化的任务读取 `docs/standards/git-worktree.md`，确认分支、工作树和已有变化归属。
4. **读取相关事实源**：按 `docs/README.md`、`specs/README.md` 和相关 `specs/<name>/` 对齐当前事实。
5. **执行任务**：实现、分析或设计时遵守规范中的门禁。
6. **同步文档**：任何行为、数据模型、UX、业务规则变化都必须回写对应文档。
7. **识别可沉淀知识**：按迭代沉淀规范判断是否更新 `docs/wiki/`、`docs/knowledge/` 或规格文档；若进入 `docs/knowledge/`，必须遵守知识治理规范。

## 与其他入口的关系

- `AGENTS.md` 定义所有 Agent 必须遵守的项目级约束，并引用本目录作为规范细则。
- `CLAUDE.md` 是 Claude 类工具的轻量索引入口，不复制规范正文。
- `docs/README.md` 定义文档分类与演进规则。
- `specs/README.md` 定义活动规格的统一入口。
- `docs/knowledge/catalog.md` 是可复用知识的索引入口。
- 本目录不替代具体规格；当任务涉及某个功能域，仍必须阅读对应 `specs/<name>/`。

## 完成定义

一轮迭代只有同时满足以下条件才算完成：

- 产出符合技术规范或业务规范。
- 相关代码、规格、设计文档保持一致。
- 已明确判断是否有知识需要沉淀。
- 若有可沉淀知识，已落入正确位置；进入 `docs/knowledge/` 的条目已更新 catalog，并在最终交付中说明。
