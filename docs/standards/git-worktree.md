# Git 与 Worktree 变更隔离规范

本规范用于防止多个任务、多个 Agent 和多个工作树的改动混在一起，避免出现“工作区有几十项变化，但无法判断哪些已提交、哪些已丢失”的情况。它适用于所有实现、修复、文档更新、评审收口和工作树清理动作。

## 1. 强制不变量

1. **一个任务只使用一个命名分支**：默认使用 `codex/<task-name>`；不得把两个独立功能放进同一分支。
2. **一个并行任务只使用一个独立 worktree**：已有工作区正在承载其他任务、存在任何真实改动，或多个 Agent 并行时，必须新建 worktree；不得在主工作区叠加实现。
3. **`main` 只作为集成基线**：实现前从最新 `main` 建任务分支；除明确的集成动作外，不直接在 `main` 开发、暂存或提交。
4. **一个提交只表达一个原子意图**：同一功能的代码、测试和文档可以一起提交；彼此独立的功能域不得混在同一提交。
5. **未引用提交不算已保存**：提交必须由命名分支指向。需要长期保留或交付的提交还必须推送远端或合入目标分支；仅能通过 commit hash 找到的对象视为高风险状态。

## 2. 开始前门禁

开始实现前必须记录并检查：

```powershell
git branch --show-current
git rev-parse --short HEAD
git status --short
git worktree list
git diff --cached --name-status
git diff --name-status
git ls-files --others --exclude-standard
```

- `git status` 非空时，先按 **已暂存 / 未暂存 / 未跟踪** 分类，并按功能域标明归属。
- Git 状态条目数量不是任务数量；不得把“63 条变更记录”表述成“63 个任务”。
- 无法确认归属的改动不得覆盖、还原、暂存、提交或随工作树一起删除。
- 只有 stat/mtime 异常时，必须通过 `git diff` 和工作区/index 内容哈希确认无内容差异，才能刷新 index 元数据。

## 3. 暂存与提交边界

- 只允许显式暂存本任务路径：`git add -- <path...>`。
- 禁止使用 `git add .`、`git add -A`、`git commit -am` 收拢未经逐项检查的混合工作区；只有用户明确要求提交整个已核对工作区时例外。
- 暂存后必须检查：

```powershell
git diff --cached --name-status
git diff --cached --check
```

- 任意层级的 `node_modules/`、`dist/`、构建目录、测试缓存、临时 worktree 产物不得进入提交；子包也不例外。确需交付的生成资产必须在任务规格或设计文档中明确。
- 不得替其他任务或 Agent 顺手提交改动。共享文件同时包含多个功能时，必须拆分 hunk，或暂停并协调唯一修改者。
- 未获得提交授权时，任务可以保留为未提交状态，但只能留在其专属分支/worktree 中，并必须精确报告剩余文件；不得遗留在 `main`。

## 4. 删除功能的完成门禁

用户明确要求删除或放弃某个功能时，必须同时检查并清理：

- 实现代码和导出入口；
- store、类型、配置和依赖；
- 测试、fixture、脚本和生成资产；
- 活动规格、任务清单和长期文档中的当前事实引用。

最后使用文件名和核心符号做全仓搜索。搜索结果为空，或剩余内容全部被明确标记为历史记录，才能声明删除完成。具有历史价值的已实施规格按 `specs/README.md` 归档；未实施的废弃草稿可直接删除并记录原因。

## 5. Worktree 与分支清理门禁

删除 worktree 或分支前，必须全部满足：

1. `git status --porcelain` 为空；若不为空，逐项确认提交、迁移或经用户明确授权放弃。
2. 目标提交由命名分支引用：`git branch --contains <commit>` 能找到预期分支。
3. 需要远端保存时，确认远端分支或目标分支已包含提交；未推送必须明确报告“仅本地保存”。
4. 已记录 worktree 路径、分支名、HEAD、目标分支和验证结果。
5. 不使用 `git worktree remove --force`、强制切换或强制删分支处理来源不明的变化，除非用户明确授权放弃这些精确路径。

任务分支只有在已合入目标分支或用户明确放弃后才能删除。发现未引用提交时，应先恢复命名分支，再进行任何清理。

## 6. 并行协作规则

- 每个并行 Agent 必须拥有明确的任务边界、分支/worktree 和文件范围。
- 主 Agent 负责共享文件和最终集成；子 Agent 不得提交其他 Agent 的变化。
- 修改 store、schema、lockfile、规范入口等共享文件前，必须重新检查最新 diff 和相关规格。
- 出现范围重叠时暂停其中一个修改者，先确定事实源和合并顺序，不用“最后一次写入覆盖”解决冲突。

## 7. 交付报告

每次交付必须说明：

- 工作分支、worktree 和 HEAD；
- 创建的提交及其是否已推送/合入；
- 实际验证证据；
- 剩余变化按功能域分类后的清单；
- 是否存在未引用提交、未跟踪文件或待用户决定的删除项。

不得只报告一个总数，也不得把“已提交”与“已推送/已合入”混为一谈。
