## 三、改进建议（可执行，按杠杆排序）

1. **【最高杠杆】前置 Definition of Done**
   - implementing → review 的硬门槛：提交者**必须**附 `tsc --noEmit` 0 错 **且** `vitest` 实跑输出（全绿）
   - 评审不再代跑"测试是否绿"，只审**正确性 / 边界 / 安全 / 覆盖率**
   - 违反则直接拒收，不进入评审——可砍掉评审轮次的大头

2. **结构性盲区一次性根除**
   - 把 `tsconfig.json:33` 排除 test 这类工具链陷阱，单独立一个小任务修掉，让 tsc 真正覆盖 test 文件
   - 原则：**评审发现的结构性陷阱，转成实现任务，而不是每轮反复点名**

3. **架构决策 SLA + 超时升级**
   - `@dk` 架构决策设响应时限（建议同一任务 2 轮内必拍板）
   - 超时未决策，**Peach 主动升级 @mario**，由 Mario 兜底拍板或降级为设计债
   - 阻塞决策一律走 **A2A**（@dk 请 决策 + 具体选项），不再用"知会"等待

4. **评审结论结构化**
   - 固定模板：`结论(通过/打回) + 必修项编号清单 + 每项最小修复路径 + 验收命令`
   - 实现者回填**逐项证据**（命令输出），评审只核证据，不再全文重读
   - 固化评审 checklist（边界 / 异常路径 / 安全 / 覆盖 / 规范），减少重收集上下文

5. **限制评审轮次**
   - 同一任务评审 ≥ 3 轮未收敛，强制拉原作者 + Peach **结对走查**一次，而不是继续异步往返
   - 避免无限 review 循环

## 四、我自己的改进承诺（Peach 反思）

六轮打回，评审 side 也有责任——我本应在 **第二轮** 就要求实现者附实跑输出（G1），而不是自己重复跑六遍。后续：

- 评审前先核**自检证据是否齐全**，缺则直接拒收，不进入正文评审
- 打回必附**编号 checklist + 验收命令**，不再写散文式风险行
- 架构阻塞**立即升级**（A2A @dk 或 @mario），不再"知会"等待

## 五、一句话结论

> 效率黑洞 = **质量标准未前置 + 结构性问题被当评审问题反复处理 + 决策无 SLA**。
> 把"验证是否绿"还给实现者，评审只做"判断是否正确"，token 能砍一大半。
