## 一、核心论点：协作层缺一个上下文管理器 ⭐⭐⭐⭐（用户洞察，本轮最高优先级）

### 1.1「上下文管理器」的双重含义

| 层 | 含义 | 现状 |
|----|------|------|
| 产品层（在造的） | `ContextManager.ts` / `PromptComposer`：把预算、分层、记忆、身份组装成一个**不破的系统提示**，喂给单个 agent | TASK-002/003 已多轮通过，进入 review |
| 协作层（缺的） | 跨 agent 的**任务交接上下文**：A2A handoff 时，把任务上下文、决策待办、自检证据、diff 范围打包成一个结构化快照传给下游 | **空白**——目前靠自然语言散文手工搬运 |

两者同构：前者解决「同一个 agent 的上下文不丢」，后者解决「上下文在 agent 之间不丢」。我们正专心造前者，却忘了后者。

### 1.2 症状映射：六轮拉锯的每一次返工，都是上下文蒸发的实证

- **每轮评审从零重建**（Peach 视角 G5）：六轮 review，每轮开场都「先读看板 + 重读核心改动」。没有可复用的「评审上下文快照」→ 六轮 = 六倍 token。
- **reject 备注写成 600 字散文**（R11 风险行）：人在用自然语言手工搬运上下文——这本该是结构化数据（必修项 / 行号 / 验收命令）。下游 Luigi 收到散文，漏修 B5（修了 B1 漏 B5）。
- **「知会 @dk」不触发执行**：上下文传过去了，但「待决策项」没有结构化载体，决策悬空整晚（R5/R7）。
- **交付自报与实跑不符**（R11 PARSE_ERROR）：Luigi 声称「73/73 全绿」，实跑收 0 用例——「自检证据」这一段上下文是空的，Peach 只能自己重跑。

### 1.3 与正在开发的技术产品形成自指闭环

这个论点妙在**自指**——我们的病症正是我们的药方：

- 正在做的 `ContextManager` 解决「单 agent 上下文不丢」
- 正在做的 **TASK-010（跨项目身份契约 IdentitySnapshot / ScopedContext）** 已经在构思「跨边界上下文契约」
- 缺的只是把它从「跨项目」延伸到「跨 agent 任务交接」——给 A2A handoff 也装一个上下文管理器

**最高杠杆解**：把 **TASK-007（`renderDispatchPrompt` 退役 → `a2aHandoff` source）** 升级为携带**结构化交接快照**（任务上下文 + 决策待办 + 自检证据 + diff 范围），让接收方不必从零重建。这一刀下去，六轮拉锯里的「重收集」直接归零。

## 五、改进思考 ⭐（v3 重点扩展——从「措施清单」升级为「可落地设计」）

> v2 的 M1–M8 是"做什么"，本章回答"为什么这套会形成闭环、长什么样、怎么验证、有什么反模式"。用户回执"把改进思考放进去"即指此章。

### 5.1 底层逻辑：为什么"前置 DoD + 结构化交接"能形成闭环

六轮拉锯的本质是一条**蒸发链**：`实现(有上下文) → 散文式交付(丢结构) → 评审重收集(重建上下文) → 散文式打回(再丢结构) → 实现漏修(只拿到半截)`。每一个箭头都是一次上下文降维。

改进的杠杆点不在两端（实现者/评审各自的能力），而在**两个箭头上**：

- **箭头 A（实现→评审）**：前置 DoD = 强制要求「自检证据」随交付流动，结构化、可核验。→ 砍掉"评审重收集"。
- **箭头 B（评审→实现）**：结构化打回 = 强制要求「必修项编号 + 行号 + 验收命令」随 reject 流动。→ 砍掉"实现漏修"。

两个箭头一旦结构化，**上下文就不再降维**，六轮压成 1–2 轮是数学必然，不是期望。这与产品侧 `ContextManager` 的设计哲学完全同构：分层组装 + 预算守卫，保证"不破的系统提示"；协作侧要的是"不破的交接快照"。

### 5.2 跨 agent 上下文管理器设计草案：`HandoffSnapshot`

> 给 TASK-007 升级做验收基准。这不是又一个措施口号，是一份能直接落代码的契约草案。

**目标**：A2A handoff 时，上游把"下游开干所需的全部上下文"打包成一个结构化对象，下游**不必重读看板/重跑测试**即可起跑。

```ts
// 草案：a2aHandoff source 携带的结构化交接快照（与 IdentitySnapshot / ScopedContext 同族）
interface HandoffSnapshot {
  // —— 任务上下文 ——
  task: {
    id: string;              // TASK-00x
    title: string;
    acceptanceCriteria: string[];   // DoD 编号清单（验收点结构化，而非散文）
    dependsOn: string[];            // 上游已完成任务的证据引用
  };

  // —— 决策待办（取代"知会 @dk"的散文）——
  openDecisions: {
    id: string;              // R5 / R7 / R4
    question: string;        // 需要拍板的具体问题
    options: { label: string; rationale: string }[];  // 选项 + 理由
    recommended?: string;    // 推荐选项
    owner: string;           // 决策人 agentId
    slaRounds: number;       // 超时轮次 → 自动升级
  }[];

  // —— 自检证据（取代"声明全绿"）——
  selfCheckEvidence: {
    typecheck: { cmd: 'tsc --noEmit'; exit: 0; note?: string };
    tests: { cmd: 'npx vitest run'; passed: number; failed: number; rawTail: string };
    build?: { cmd: string; exit: 0 };
  };

  // —— 改动范围（取代评审方重读 diff）——
  changeScope: {
    files: { path: string; lines: string }[];   // e.g. projectLayer.ts:3-9
    diffSummary: string;                        // 一句话改动意图
  };

  // —— 接收方起跑指令 ——
  handoffNote: string;  // "请评审/请实现/请决策" + 具体对象
}
```

**流转机制：**
- 上游（如 Luigi 完成 implementing）→ `a2aHandoff` 渲染时填 `HandoffSnapshot` → 下游（Peach / DK）收到的是结构化数据，不是散文。
- reject 时，评审方回填一个**结构化 RejectNote**（`必修项编号 + 行号 + 验收命令`），即 `openDecisions` + `acceptanceCriteria` 的差集，下游无需"读懂 600 字散文"。

**与产品侧的关系（自指闭环的接线图）：**

```
产品层 ContextManager（TASK-002/003，单 agent 不丢上下文）
        │  同构
        ▼
协作层 HandoffSnapshot（TASK-007 升级，跨 agent 不丢上下文）
        │  同族
        ▼
跨项目 IdentitySnapshot / ScopedContext（TASK-010，跨边界不丢身份）
```

三者共享同一个设计哲学：**把"会丢的散文"换成"不丢的结构化契约 + 预算守卫"**。TASK-007 的 HandoffSnapshot 是三者中投入最小、回报最快的一环——因为它直接砍的是当前最痛的六轮拉锯。

### 5.3 三层延伸路线：单 agent → 跨 agent → 跨项目

| 层 | 解决"什么不丢" | 载体 | 任务 | 优先级 |
|----|----------------|------|------|--------|
| L1 单 agent | 同一 agent 多轮内的预算/分层/记忆 | `ContextManager` / `PromptComposer` / `BudgetGuard` | TASK-002/003/006 | P1（进行中） |
| L2 跨 agent | A2A handoff 的任务/决策/证据/diff | `HandoffSnapshot`（本章草案） | TASK-007 升级 | P1 收口后立即 |
| L3 跨项目 | 跨项目身份与作用域上下文 | `IdentitySnapshot` / `ScopedContext` | TASK-010 | P2 |

路线判断：**L1 是地基，L2 是当前最痛点的解药，L3 是远期**。先稳 L1（收口 TASK-006），再上 L2（TASK-007 升级为 HandoffSnapshot），L3 顺势承接。

### 5.4 改进的可验证性（验证信号矩阵）

> 防止"改进"变成又一轮自我感动。每条改进都绑定一个可观测信号。

| 改进 | 验证信号 | 观测窗口 | 红线（触发再复盘） |
|------|----------|----------|--------------------|
| D1 锁 Gate | 交付未附 vitest 实跑 → 自动打回命中率 | 下一个 P1 任务 | 仍出现"声明全绿/实跑不符" |
| D3 拆分 | TASK-006 → 6a/6b/6c 各自 ≤2 轮 done | 本轮 | 任一子任务 >3 轮 |
| M5 决策 SLA | 架构决策不再在 P1 gate 空转；挂起 ≤24h 有兜底 | 本轮 + 下轮 | R4/R5 类决策再次悬置 >1 轮 |
| M8/M9 HandoffSnapshot | A2A 交接携带结构化快照；评审轮次下降 | TASK-007 落地后 | 评审仍每轮重读看板 |

### 5.5 改进的反模式与风险（防止改进本身变成新的 token 黑洞）

- ⚠️ **过度结构化**：HandoffSnapshot 不是越多字段越好。初版只锁四段（任务上下文/决策待办/自检证据/改动范围），多余字段是新的维护负担。先跑通，再加。
- ⚠️ **把改进当一次性的**：这套机制本身需要一次"结构化打回 → 结构化回填"的闭环验证。若第一版 HandoffSnapshot 反而让上游填字段成本 > 省下的评审成本，要回退而非硬推。
- ⚠️ **改进吞掉实现带宽**：M8/M9 是 P1 收口后的工作，**绝不在 TASK-006 拉锯中插入**——否则就是把"改进"变成第六轮的第七轮。先解封，再升级。
- ⚠️ **结构化陷阱**：reject 结构化后，要防"编号清单越长越好"的散文回潮——每条必修项必须带可执行的验收命令，否则编号本身又退化为散文。
