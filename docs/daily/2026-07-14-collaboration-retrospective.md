## 二、根因诊断（按杀伤力排序）

### 根因 1 ⭐⭐⭐　Gate 标准双向不一致（最致命）
- Luigi 的"完成"标准 ≈ `tsc --noEmit` EXIT 0 + 部分测试绿
- Peach 的"通过"标准 ≈ `vitest` 全量实跑 + 证据
- **但 tsconfig 把 test 文件整体 exclude 了**，所以 `tsc EXIT 0` 对测试正确性零证明
- 后果：Luigi 反复拿 tsc EXIT 0 当通过证据交，Peach 一实跑就挂 → 每一轮都是"双方各烧一次完整推理"。**这一个根因解释了六轮拉锯里至少一半。**

### 根因 2 ⭐⭐⭐　交付自报与实跑不符 → 信任坍塌
- R11 的 PARSE_ERROR（`promptComposer.test.ts:540-547` 孤立 `expect(result)` + 多余 `});`）让整个 promptComposer 套件收 0 用例，而交付声明全绿
- B1（await 方向）修复本身方向正确，却引入新 parse 回归 → **说明改完没跑全量就交**
- 信任坍塌的连锁反应：Peach 不再信任自报 → 评审从"抽查"退化成"全量重测" → 每个 review 都是 Peach 重跑一遍 → **token 翻倍**

### 根因 3 ⭐⭐　架构决策空转
- R7（projectLayer id 守卫 A 防御式 / B 契约式）、R5、R4 三个决策长期挂"待 @dk 拍板"
- DK 未被有效拉入 / 决策迟迟不来；Peach 用"并入 R11 B5 收口"绕过，但 B5 措辞又漏了 `projectLayer.ts:3` 守卫项 → **验收标准本身有洞** → 每轮重新加载同一上下文
- 决策债务越埋越深，从 P1 gate 漏进风险表，反复占用评审带宽

### 根因 4 ⭐⭐　收口任务过载 + 串联太重
- TASK-006 一个任务挂 6 轮，依赖 TASK-003/005，还把 R6/R7/B5 全塞进来
- 一个点挂 → 整条 P1 全卡 → P2 全 todo（"P2 启动前置 = P1 全绿"）
- **没有可并行的切片**，全队串在一根线上，谁都动不了

### 根因 5 ⭐　状态机噪音
- TASK-004 横跳、TASK-006 六轮，每次状态变化触发系统通知
- 通知 ≠ 进展，但每条都在消耗注意力预算，制造"很忙"的错觉

- **知会 @dk：R7 已按 A 拍板，如无异议即落地。R5/R4 维持 P2 债务，不阻塞 P1。**
