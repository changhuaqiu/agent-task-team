# Project 与工作项分层决策

> Status: Implemented
> Date: 2026-08-31
> Active spec: `specs/project-workitem-hierarchy/`

## 一、问题

Project 当前默认打开一条常驻协作流，Project 下的 Issue、变更、改进、Task、Agent 回复和运行事实缺少可见父子层级。
这使用户无法回答“这条讨论属于哪项工作”，也使 Agent 容易把其他工作项的历史带入当前执行。

这不是筛选器问题。Project、工作项和讨论线程承担不同职责，必须在对象模型和界面层级上分开。

## 二、用户对象模型

```text
工作区
└── Project（长期目录、仓库、成员和汇总边界）
    ├── 概览（进度、风险、近期工作）
    ├── 工作项（Issue / 变更 / 改进）
    │   ├── 目标与验收条件
    │   ├── Task / Subtask
    │   ├── 按角色分列的交付件
    │   ├── Review / Gate
    │   └── 独立活动与讨论
    ├── 项目交付（跨工作项的产物、评审与发布聚合）
    ├── 项目活动（只读聚合）
    └── 设置
```

- **Project** 是长期容器，不是聊天房间。
- **工作项** 是用户要求团队完成的一件事，是讨论、执行和完成判断的默认边界。
- **Task** 是工作项内部的执行拆解，不代替工作项。
- **活动/讨论** 必须显式归属于 Project 或工作项；Project 活动只聚合，不接受会改变工作归属的自由输入。
- **产物、评审和发布** 是可引用事实，必须关联工作项；Project 页面只提供聚合视图。

## 三、界面决策

1. Project 默认打开“概览”，首先展示进行中、需要处理、待评审和近期工作项。
2. “工作项”是 Project 内主入口。列表按状态组织；打开一项后显示目标、子任务、角色交付与该工作项的活动。
3. Project 不再默认挂载全局聊天输入器。“项目活动”仅展示跨工作项聚合事实。
4. 工作项活动输入器只写入该工作项的内部协作空间。切换工作项时草稿和消息上下文同步切换。
5. 项目交付件先按贡献角色分列，每列内部再按实现、设计与文档、验证与评审、外部交付分类；证明材料不混入正式交付件。
6. Review 指向明确工作项和产物版本；没有关联时可在 Project 聚合页发现，但不能伪装成某项工作的完成证据。

## 四、外部 Issue

- GitHub Issue 是工作项来源，不是新的 Project。
- 接入时按仓库根目录查找或幂等创建 Project，然后在该 Project 下创建一个独立工作项活动空间。
- Issue 已接收但 Agent 尚未产生根 Task 时，工作项仍立即可见，并明确标记为“等待任务规划”。
- 同一仓库的后续 Issue 复用同一 Project；同一 Issue 的重复 webhook 复用同一工作项。
- Issue 标题、正文、验收清单、URL 和编号保留为工作项来源事实。

## 五、旧项目迁移

- 已有 Project 无需重建。
- 已关联 Project 的非 workspace Conversation 继续作为工作项内部活动空间，但不再向用户展示 Conversation 名称。
- 现有 Project workspace 上的顶层 Task 各自投影为旧工作项；历史 Project 消息保留在“项目讨论（历史）”，不自动混入新工作项上下文。
- 新建工作项从创建时即获得独立 workstream；迁移兼容层退出条件是所有可执行工作都能解析到明确工作项空间。

## 六、成功标准

- 用户从 Project 两步内进入任一工作项及其讨论、任务和交付件。
- 两个工作项的消息、草稿、Agent Invocation 和完成事实不会互相串流。
- Project 页面没有默认群聊输入器，项目活动能按工作项追溯。
- GitHub Issue 不重复创建同仓库 Project。
- 旧 Project 和旧任务无需用户重建即可在新层级下被发现。
- 任务完成率评测能以工作项为样本边界，路径长度和失败阶段可稳定归因。
