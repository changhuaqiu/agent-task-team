# 评估作为平台内建工作区的 UX 决策

> Status: Implementing
> Date: 2026-07-19
> 关联规格：`specs/agent-eval-system/spec.md`
> 关联决策：`docs/product/ux/2026-07-16-right-panel-ia-simplification.md`

## 用户问题

评估来自当前 Agent 平台中的项目、任务、协作链、执行证据和配置版本。若把它设计成外部系统，用户需要重新选择项目、复制运行材料并理解第二套对象；若把数据集、实验、复核和提案继续塞进项目右侧栏，则会让本就承载任务上下文的窄面板再次变得零散。

当前平台没有用户、成员或角色权限体系。因此本迭代不能凭空引入“评估负责人、审核者、管理员”登录或授权流程，也不能用虚构角色阻塞平台内正常使用。

## 决策

评估是 Agent 平台的内建项目能力，不是独立产品：

```text
Agent 平台
└── 当前项目
    ├── 协作工作区
    │   ├── 群聊 / 任务执行
    │   └── 任务上下文与调试
    └── 评估工作区
        ├── 结果
        ├── 数据集
        ├── 对比实验
        ├── 待复核
        └── 改进提案
```

- 左侧项目选择保持不变；进入评估时仍然作用于同一个当前项目。
- “协作 / 评估”是项目主内容区的工作模式切换，不占用项目右侧栏一级 tab。
- 单次结果默认展示关键门、证据覆盖和可回放记录；实验对象按需进入次级视图。
- 评估服务直接读取平台事实源，不要求导入平台已经拥有的任务或 trace。
- 改进提案只记录假设、回归与回退证据；评估服务不直接修改 RoleCard、Skill 或平台策略。

## 权限与身份边界

当前产品没有权限管理，本迭代采用以下真实边界：

- 所有读写必须校验对象属于当前 `conversation/project`。
- 变更动作的审计字段使用平台本地操作者占位身份，明确表示“当前平台用户”，不接受请求伪造管理员角色；当前不提供人工 annotation UI/API，不用自由文本姓名伪造审核者身份。
- 不新增登录、RBAC、管理令牌或角色配置 UI。
- 若平台未来建立统一身份与项目成员事实源，人工校准必须同时接入独立审核流程和真实工作区入口；在此之前，规格中的角色矩阵是未来约束，不是当前退出门。

## 放弃方案

| 方案 | 放弃原因 |
|---|---|
| 独立评估产品或外部控制台 | 重复项目与配置上下文，割裂主流程 |
| 在右侧“调试”里堆完整实验系统 | 窄面板无法承载成对 diff、分层统计和复核队列 |
| 给右侧栏再加一个“评估”一级 tab | 与既有“右面板收敛为任务 + 调试”的 IA 决策冲突 |
| 当前迭代新增评估 RBAC | 平台没有身份/成员事实源，会制造虚假安全模型 |

## 技术与 UX 约束

- `conversationId` 是平台项目上下文键，评估页面不重复询问项目。
- 项目工作模式切换是展示状态，不新增另一份项目 store。
- 右侧栏继续承担任务上下文和诊断，不承载成熟实验对象。
- 数据集、实验、复核和提案通过评估服务/API 读取同一 SQLite 事实，UI 不复制业务规则。
- 没有数据时只显示当前视图的单一空态，不预渲染所有对象的空卡片。

## 成功标准

- 用户在同一个项目内切换“协作 / 评估”，项目选择和运行上下文不丢失。
- 右侧栏没有新增评估一级 tab，也不重复出现单次评估入口。
- 评估工作区能访问结果、数据集、实验、待复核与改进提案。
- API 继续执行项目归属校验，但产品中不存在虚构权限配置。

## 当前操作闭环

- “待复核”支持在线失败案例批准/拒绝晋升，并要求填写可审计依据。
- Judge 分歧支持 `pass / partial / fail` 人工裁决并保存理由。
- Gap 可生成 draft proposal；proposal 支持提交、单一平台操作者明确确认批准/apply 和回退。
- 不满足可信 held-out、执行来源或逐例盲测门时，服务端阻止 proposal 批准/apply。

## 结果页信息架构纠偏

用户反馈原结果页过于复杂。真实页面首屏同时展示历史运行、五个门禁、综合分、覆盖率、数据质量、所有评分维度、证据 ID、改进建议和重放动作，迫使用户自己拼出结论。

结果页采用渐进披露：

```text
本次结论
├── 通过 / 未通过 / 证据不足 / 评估未完成
├── 影响结论的原因
├── 已观察到的表现
└── 下一步

完整评分与证据（默认收起）
├── 全部门禁
├── 全部评分维度
├── 数据质量与证据引用
└── 冻结证据重放
```

约束：

- 门禁为 `unknown`、评估为 `partial` 或证据不完整时，主结论必须是“证据不足”，不能以高综合分作为标题。
- `overallScore` 在证据不完整时显示为“已评维度得分”，只作诊断。
- 首屏只展示影响结论的适用门禁；`not_applicable` 不伪装成问题。
- 只展示有数值且适用的表现指标；未知/N/A 维度进入完整详情。
- task/span/pass/proof 等内部证据 ID 默认收起，用户主动查看证据时才出现。
- `35/35 次工具执行成功` 的用户名称是“工具执行成功率”，不是“执行效率”。
- 历史运行使用单一选择器，不再平铺多个分数卡片。

## 2026-08-21 根任务绑定与协作诊断

- “重新诊断”始终绑定当前 Delivery 的根任务；没有根任务时按钮禁用，并用一句用户可理解的原因说明，不退化为项目全历史评估。
- 当前 DeliveryRun 在项目工作区公共层加载，切到评估模式或在评估模式中更换项目都不依赖协作面板先挂载。
- 历史报告可只读浏览；查看历史不要求当前 Delivery 仍有活动根任务，只有创建新的在线评估需要根任务。
- 首屏表现指标增加交接回执、分支完成、并行汇合、恢复健康和重复返工；Agent 贡献画像只进入诊断详情，不呈现为人员排名。
