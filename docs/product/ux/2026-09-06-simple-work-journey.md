# 从目标到查收：简单工作闭环

> 状态：已实现；固定样本及已有项目桌面验证通过，已集成主分支。
> 历史实施契约：[体验整改](../../archive/specs/ux-journey-completion/spec.md)

用户不是来管理运行记录的，而是把一个明确目标交给团队并查收可信成果。入口只回答四件事：要做什么、谁接手、现在需要我做什么、成果在哪里。

项目是长期目录与团队，工作项是一次目标，执行任务是团队拆解。旧项目继续使用，不要求重新创建。所有工作项数量与导航复用同一读模型；共用历史讨论空间不等于同一个工作目标。

创建成功只代表目标被记录。开始安排是显式的人类意图，由服务端命令接纳；页面不能把本地按钮成功称为团队已开始。职责和本机登录继承在需要时解释，不用内部运行术语占据首屏。

当前问题与历史记录分开：任务阻塞、未解决人工请求必须带来源和下一步；曾经接纳、曾经等待不能常驻为当前状态。根目标进行中而执行子任务阻塞是合法事实，分别呈现，不强改状态。

工作详情分为目标与任务、活动、成果与验收。执行任务可直接打开，阻塞操作以原因和恢复条件为先；改派/拆分/删除是次级操作。成果按贡献角色分列、再按用途分类，可阅读实际内容并返回所属工作；证明材料与成果登记状态保持区别。

验收来源于结构化 Task Gate、冻结结果包与被决定接纳的证据。空 ProjectReview 不代表没有 Task Gate；聊天声称通过不代表已接纳验收。缺失的历史证据诚实展示。发布和自动化仍可使用，但不是完成一次工作的必经步骤。

不采用：新增仪表盘堆卡片、恢复项目大群聊、自动替用户授权、解析 Agent 自述生成通过结论。验证结果在本轮评测中记录后才进入 STORY 和 README。

## 一次工作的四步体验

1. 连接项目目录：创建的是长期项目，不是大群聊。
2. 创建工作项：先记录目标，再点“交给团队安排”；不把保存记录算作 Agent 开始。
3. 查看进度：概览只报当前事实，阻塞可直达具体任务；历史交接另读。
4. 查收成果：从已完成工作进入“成果与验收”，阅读决定依据与实际文件；发布按需使用。

已读只改变阅读标记，不解决任务。返回/刷新保存项目、工作、详情页和通知定位；目标数据尚未加载或已删除时，不拿其他工作项代替。普通工作根任务优先用 work.created 的持久事实绑定，不能让同毫秒子任务排序改变目标。

目录选择支持粘贴路径、原生按钮键盘选择；只浏览当前用户目录内的真实目录。任务当前阻塞原因只读，修改与重试走明确命令。高级拆分、改派和删除从主阅读路径收起。
