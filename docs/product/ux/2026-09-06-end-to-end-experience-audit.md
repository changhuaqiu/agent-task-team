# 全流程体验走查：从项目接入到交付验收

> 日期：2026-09-06（Asia/Shanghai）
> 状态：体验审计；整改方案待实施，不能作为修复完成证明
> 代码基线：`59850ef`

## 1. 结论与用户场景

目标用户是希望把一项软件改进交给 Agent 团队、只在必要决策时介入的开发者。成功体验应让用户随时回答：我交给团队什么目标、谁正在处理、卡在哪里、我需要做什么、最终成果和验收证据在哪里。

当前已经具备 Project → 工作项 → 任务与活动的可见结构，也具备角色交付列、创建草稿保护和运行记录。但跨页面的数量与状态口径、旧工作项导航、阻塞处理路径和最终验收入口尚未连通。用户仍需要自己解释状态、查找恢复动作、从聊天和文件引用中拼接交付结论。

优先应修复身份和事实呈现，再打通开始、恢复、验收的操作路径；视觉细节在这些路径稳定后调整。

## 2. 检查方法与边界

- 连接当前正在运行的 Windows EXE 所属 Node Service，通过浏览器检查同一服务的共享 Renderer。通过进程父子关系与监听端口确认服务归属；本次观察地址为 `http://127.0.0.1:56647/`，该端口不是稳定产品入口。
- 实际浏览两个既有项目；主要样本为 agent-interview 中的“优化项目结构及UX”、两个已完成的旧工作项和一个待处理工作项。
- 实际操作：项目浏览/添加表单、工作创建表单及草稿保护、账号 OAuth/API Key 表单、执行环境列表、Agent 资料、项目概览、工作项切换、活动、阻塞通知与任务抽屉、项目/工作项交付件、评审、发布空态、自动化创建预览。
- 使用可访问性树与实际截图观察页面；结合以下组件和读模型核对原因。没有用 README 声明代替产品验证。
- 没有提交项目/工作/账号/自动化创建，没有发送 Agent 消息、执行恢复、改变权限或重新运行真实用户任务。浏览器正常进入收件箱条目可能按产品既有行为标记已读。
- 没有覆盖原生窗口的安装、冷启动、托盘、系统通知、退出恢复、深链和不同屏幕尺寸；本轮也没有从空数据库完成首次注册、真实 OAuth 登录或从新任务生成新交付。因此这是全流程界面与实现审计，不是一次新任务执行成功率实验。

## 3. 逐阶段结果

| 阶段 | 已观察到的有效体验 | 主要断点 |
| --- | --- | --- |
| 接入账号与执行程序 | 账号列表优先；OAuth/API Key 字段分支正确；程序依赖检查有结果 | 账号页显示无账号，Agent 又显示可协作；继承已有登录态没有在上手路径解释 |
| 添加项目 | 先浏览已有项目再连接新目录 | 项目入口发现性较弱；新项目说明仍承诺进入协作流，与概览默认页不一致 |
| 创建工作 | 只需标题，说明可选；关闭未提交草稿会确认 | 没有说明创建后谁接手、是否已经开始、下一步在哪里；类别仍用英文 |
| 看进度与拆解 | 工作项列表分组、子任务状态和依赖可见 | 统计口径冲突；子任务列表为不可打开的静态行；异常提示不能直达处理 |
| 协作与异常 | 回复按调用组织，工具过程折叠；有原始运行详情 | 已接纳、阻塞、等待决定来自不同层级且没有说明；恢复按钮藏在更深抽屉 |
| 查收成果 | 已按贡献角色分列，再分实现/文档等类别；支持搜索 | 文件只能复制引用，关联工作不是链接；日志/配置落入“其他”；缺少验收汇总 |
| 评审与完成 | 保留任务完成、交付登记、评审等独立事实 | Gate 结论与项目评审页分离；用户看不到一份解释“为何完成”的结果页 |
| 发布与自动化 | 发布说明明确可选；自动化有自然语言预览且默认关闭 | 高级入口与日常工作并列；需要后续验证真实运行、审批和恢复链 |

## 4. 确定缺陷与整改建议

### UX-01 · P1 · 工作数量与进行中口径冲突

**复现：**同一 agent-interview 项目，侧栏为“13 个工作项”，项目卡为“13 工作”，工作项列表/概览为“4 项工作”。列表只有 1 项进行中、1 项待处理，概览却显示“进行中 2”。

**原因：**`ProjectSidebar.tsx` 的 `workCountByProject` 遍历所有 Task；`ProjectsOverview.tsx` 的项目卡同样使用 `projectTasks.length`；列表使用 `projectWorkItems()` 聚合。`ProjectOverviewSurface.tsx` 把 ready、proposed、in_progress 一起计入“进行中”。

**建议：**全局和项目页统一使用工作项数量；子任务数量单独命名。“进行中”仅表示实际进行中；如需包含排队，文案改为“未完成”，并保留细分状态。

**验收：**具有 4 个工作项、13 个 Task 的固定数据，在侧栏、卡片、概览和列表均显示 4 个工作项；1 个 in_progress + 1 个 ready 不显示为 2 个进行中。

### UX-02 · P1 · 旧工作项导航丢失对象身份

**复现：**从“优化项目结构及UX”列表点击已完成的“增加在线面试功能”，一次退回项目概览；再从概览点击“增加在线面试功能”，显示了“支持从微信公众号导入面经并进行解析”。在同一旧会话中再次点击正确列表项，才进入目标详情。

**原因：**`ProjectWorkspace.tsx` 根据选中会话是否为项目 workspace 切换 `ProjectObjectWorkspace` 的 React key，跨新旧工作会触发重建。概览的 `onOpenWork` 只保存 conversationId、不传目标 taskId；多个旧工作共享会话，`ProjectWorkItemsWorkspace.tsx` 会退回匹配该会话的第一个对象。本地选中 key 不能跨重建保留。

**建议：**导航由 Project + WorkItem 的复合身份驱动；页面 tab 与任务选择保持稳定，不能用会话是否为 workspace 决定重建整个页面。从收件箱打开子任务时应定位所属工作项并打开该子任务。

**验收：**覆盖新工作→旧工作、旧工作 A→B、概览直达、收件箱直达、返回/刷新；标题、活动、交付件和草稿始终归属所点击对象。

### UX-03 · P1 · “需要处理”没有统一事实口径

**复现：**项目概览显示“需要处理 0”，顶部却显示“用户 → Mario · 交接被阻止 / 等待你的决定”；收件箱“需要处理”中还能看到 DK 的已阻塞任务。工作项详情顶部为“DK · 已确认接纳”，下方任务列表同时有已阻塞与待确认。

**原因：**概览只统计根工作项 `status === blocked`，不消费子任务阻塞、人工决策或收件箱可行动事实。`A2APossessionStrip.tsx` 按时间取最近交接/回执/失败记录作标题，历史回执没有等价于当前执行状态的保证。检查中找到 8/31 的历史决策请求，顶栏只显示时刻，没有让用户识别其日期和所属目标。

**建议：**保留不同事实的语义，统一派生“当前需要人处理”集合；显示问题、所属工作项、当前状态、发生时间和唯一主操作。历史接纳回执移入记录，不替代当前执行状态。

**验收：**根工作进行中但子任务阻塞、旧决策已被后续工作取代、Agent 已结束但历史 ack 仍在三种场景，不再同时出现误导性的零待处理与当前阻塞提示。不能靠强改根任务终态来统一数字。

### UX-04 · P1 · 阻塞可以读到，但处理路径过深

**复现路径：**收件箱“需要处理”→阻塞条目→工作项详情→活动→找到阻塞回复→“跳转到任务”→任务抽屉，才出现“恢复任务”和改派。工作项概要里的执行任务行是静态 div，没有点击/键盘打开入口。

任务抽屉同时展示恢复、取消、改派、拆分、合并、流转到开始/取消/恢复待处理、删除和 Agent 控制台。对于本例“验收命令执行权限被拒”的问题，界面没有解释恢复任务与解决权限问题的区别。

**建议：**概要直接展示当前阻塞摘要和“查看并处理”；子任务行可直接打开。抽屉优先展示原因、负责人、恢复条件和与原因匹配的下一步；拆分、合并、删除与终端放入次级操作。恢复不得自动扩大权限，也不能只改状态后再次失败。

**验收：**从任一阻塞提示两次操作内进入确切处理面；未解决权限前不显示“已恢复执行”；真实授权、改派或重试后的回执原位可见。

### UX-05 · P1 · 已完成结果缺少可查收的验收页

**复现：**“增加在线面试功能”显示已完成；详情只有目标和任务列表，交付件页列出 6 个引用，项目评审页却显示“没有评审”。Agent 活动里存在 Gate 通过说明，但用户必须自己回翻才能了解依据。

**原因：**工作项详情只有 summary/activity/artifacts 三个视图；`ProjectReviewSurface.tsx` 读取 `/api/reviews` 的 ProjectReview，无法代表所有 Task Gate。两套事实没有在工作项结果上汇聚。这里不能由“项目评审为空”推断“没有任何 Gate”。

**建议：**工作项结果页统一呈现目标逐条验收、已接纳 Gate/Review、验证方式和时间、版本、交付入口与未覆盖风险。ProjectReview 与任务 Gate 保持领域边界，但让用户能沿同一工作目标查到二者。

**验收：**有 Gate 而无 ProjectReview 的已完成工作仍可直接查看完成依据；无证据的历史工作明确显示缺口，不伪造通过结论。每项验收都能打开对应来源。

### UX-06 · P2 · 交付件已分类，但仍停留在引用账本

**复现：**角色列正确显示 Mario 与 Luigi；文件详情只有“复制引用”，关联工作为普通文字。`server-e2e.log`、`store.json`、`package.json` 落入“其他”，日志和配置没有表达其业务用途。

**原因：**`ProjectArtifactSurface.tsx` 的 ArtifactDetail 没有打开/预览/定位工作动作；列通过 updatedBy 归属贡献者，类别依赖 kind。最后登记者是否等同实际贡献角色，需要在后续数据模型验证中明确，不能仅凭名字推定错误。

**建议：**保留现有角色列，文件支持预览/打开所在位置，报告支持阅读，外部交付支持打开链接；关联工作可直达。以用途与来源补齐日志、配置等类别，并区分正式成果与证明材料。

**验收：**用户从已完成工作两步内打开成果和验收报告；无法打开时明确说明原因；搜索后角色归属不丢失，同一文件版本与证据来源可以追溯。

### UX-07 · P2 · 首次使用没有闭合“配置→创建→开始”

**复现：**账号设置显示“还没有账号”，运行环境显示三个程序“可使用”，Mario 资料显示“可协作”。三者可以同时成立，但首用界面没有解释继承本机登录态。Agent 列表卡片首要信息为执行程序和技能数，职责需要进入“信息”才能看到。

创建工作仅有类别、标题、可选说明；成功回调选中会话并打开工作 tab。服务端 createWork 创建的根任务 `agent_id` 为空；本轮没有提交新工作，因此不据此断言所有创建都不会被自动化接手。确定问题是当前表单和概要没有告诉用户创建是否包含开始执行、谁会统筹、如何确认接手。

**建议：**建立紧凑的上手就绪摘要，说明使用已登录配置或需要补齐什么；卡片优先显示协调/实现/验证职责。创建后明确显示“已记录，等待安排”或有权威依据的“Mario 已接手”，并给出下一步；保留轻表单，验收内容允许渐进补充。

**验收：**全新用户不依赖口头教程能完成一项工作创建并确认是否开始；本机继承登录与显式账号两条路径均可解释；记录成功不得冒充执行接纳。

### UX-08 · P2 · 活动浏览缺少精确回到上下文的路径

**复现：**收件箱包含大量同一 Agent 的过程更新、截断标题和摘要重复；点击阻塞条目只到工作项，未打开确切阻塞任务。项目聚合活动的条目为截断正文和标签，没有返回对应讨论位置的操作。

**原因：**`ProjectsOverview.tsx` 非 work 类型的收件箱条目只调用 onOpenProject；`ProjectActivitySurface.tsx` 使用不可点击 article 与三行截断正文。`ProjectWorkItemsWorkspace.tsx` 的选中对象以工作项为单位，子任务身份没有完整转化成详情定位。

**建议：**收件箱优先可行动变化，每个条目带目标工作名、结果/异常摘要和精确定位；过程信息按一次响应折叠。项目活动支持打开所属工作项及消息，不把被截断正文当作阅读终点。

**验收：**消息、Gate、Review、子任务、产物五类通知均进入正确对象/位置；单纯看过与已经解决分开；过程回复不会挤掉待决策事项。

### UX-09 · P3 · 文案、主动作与可读性仍需统一

- 概览同时显示头部“创建工作”和卡内“创建工作项”；自动化空态也有两个创建入口。
- 工作/工作项、交付件/产物、Project/Projects、Agent teams 等中英文混用；工作类别出现 Change request / Improvement；新项目说明仍写“进入项目协作流”。
- 工作列表与状态摘要存在大量 9–11px 次要信息和截断描述，尤其长任务名与依赖名难以阅读；子任务不是可展开项。
- 创建项目的目录选择面展开大量目录，部分图标按钮没有可访问名称。账号新增弹窗的关闭按钮也没有名称。

**建议：**定义一份用户术语表；每个页面保留一个明显主动作；提高关键状态与任务名的可读性，长内容按需展开；为图标补名称。目录选择提供直接粘贴路径入口的价值应结合实际组件进一步验证。

**验收：**键盘能完成创建、选择任务和关闭弹窗；常用桌面尺寸下无需横向猜测长标题；标签与 README 上手说明一致。

## 5. 应保留的设计

- Project 默认概览、工作项独立活动与按任务作用域组织的方向正确；不应恢复项目级公共聊天作为所有目标入口。
- 角色列→业务类别→产物→详情的结构已经可以实际观察，应补齐内容和操作而保留此结构。
- 工作创建已有未提交草稿保护，OAuth/API Key 已做条件字段，均是可继续复用的交互。
- 工具过程按响应折叠，保留独立运行详情；验收不能用 Agent 的自述或程序退出替代。
- 发布是可选流程；自动化有自然语言预览、保存后默认关闭。这两个边界应继续保持。

## 6. 建议实施顺序与下一轮验证

1. **统一身份与事实：UX-02、UX-01、UX-03。**先解决点错对象、数字冲突、待处理漏报。以当前新旧项目混合数据为固定回归样本。
2. **完成最短操作路径：UX-04、UX-05、UX-06。**从阻塞直达处理，从完成直达结果，保持状态门禁与权限边界。
3. **补首用与日常阅读：UX-07、UX-08、UX-09。**做一次空数据首用和一次已有项目回访，检查无需作者解释即可使用。

下一轮评测分开记录：首次工作开始所需操作数/时间、目标对象导航正确率、阻塞原因定位时间、恢复到接纳的成功率、已完成工作证据可访问率、跨页面数量一致性。时间类指标需要实际计时；本轮不提供虚构分数、完成率或改善百分比。

新增真实端到端样本至少包括：一个普通目录项目、一组共享旧会话的工作项、一个 Git 模式项目、一个无可用账号/执行程序场景、一个权限阻塞场景、一个通过/打回的 Gate 场景。模型任务完成率另用固定任务集与应用快照评测，不能由这次界面走查推导。
