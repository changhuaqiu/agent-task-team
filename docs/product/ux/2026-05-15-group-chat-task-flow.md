# 群聊式任务流 UX 方案

> Status: Baseline implemented
> Date: 2026-05-15
> Source spec: `specs/group-chat-task-flow/`

## 产品判断

Agent 协作应当以群聊形式呈现，保留团队在场感、角色人格和轻量趣味；但用户真正需要管理的是任务流，而不是逐条聊天。

因此 UX 原则是：

> 群聊是现场，任务图是白板。

用户看到的是一支 Agent 团队在群里推进工作；系统背后用 Task Graph 维护拆分、依赖、并行、交接、阻塞、合并和复盘。

## 目标用户

- 独立开发者或小团队负责人。
- 希望通过自然语言下发目标，再让多 Agent 自动拆解和推进。
- 需要看到过程的趣味性，但不能失去可控性和可解释性。

## 核心场景

### 1. 下发一个复杂任务

用户在群聊输入：

```text
帮我重构 A2A，让 agent 协作更顺，而且群聊体验更有趣。
```

系统表现：

- 群聊中出现用户消息。
- 协调 Agent 回复简短判断。
- 聊天内出现一个根任务胶囊，例如 `#T1 A2A 群聊协作重构`。
- 右侧或下方任务地图出现根任务节点。

### 2. Agent 拆分任务

协调 Agent 在群聊中说：

```text
我把这个拆成四条线：协作模型、任务图、群聊 UI、失败处理。
```

系统表现：

- 群聊出现「任务拆分」事件卡。
- 事件卡展示 4 个子任务胶囊。
- 任务地图从根任务 fan-out 到 4 个子节点。
- 每个子任务显示状态、负责人和依赖。

### 3. 多 Agent 并行工作

不同 Agent 在群聊里接活：

- 架构 Agent 认领 `#T2 协作模型`
- 前端 Agent 认领 `#T4 群聊 UI`
- 测试 Agent 等待 `#T2` 和 `#T4`

系统表现：

- 群聊保留自然语言和一点角色语气。
- 每条关键消息附带任务胶囊。
- 任务地图显示多个 `running` 节点。
- 等待中的任务显示“等待 #T2 / #T4 完成”。
- 当某个 Agent 更新任务状态、评审说明或产出路径时，群聊自动出现一条任务通知，知会当前负责人、统筹、评审或下游依赖负责人；这不是交接，不会强行启动另一个 Agent。
- 当任务已经有明确下一位负责人或评审人，但没有新的 A2A 交接时，系统可以发一条「系统轻推」并唤醒该角色继续推进；这不是中央调度，不会替团队猜 owner。

### 4. 交接与阻塞

Agent A 把任务交给 Agent B：

```text
我已经定好状态机。#T2 交给工程 Agent 实现，约束在交接包里。
```

系统表现：

- 群聊出现「交接」事件卡。
- 任务卡显示“正在交给工程 Agent”。
- 只有接收方开始执行后，任务 owner 才变化。
- 如果失败，显示可执行原因：未配置账号、目标正忙、团队规则阻止、运行端不可达。

### 5. 分支合并

多个任务完成后，协调 Agent 发起合并：

```text
#T2 状态机 和 #T4 群聊 UI 可以合并成 #T8 A2A 群聊闭环评审。
```

系统表现：

- 群聊出现「合并提案」事件卡。
- 用户可确认或让指定 Agent 继续。
- 原任务不消失，任务地图显示它们 `merged_into` 新任务。

## 信息架构

### Group Chat Stage

主视图，承担在场感与操作入口：

- 会话消息流
- Agent 发言
- 任务胶囊
- 任务事件卡
- 快捷输入和快捷动作

默认只展示关键进展，执行日志折叠到详情。

### Task Map

辅助视图，承担结构理解：

- 根任务与子任务
- 依赖关系
- 并行分支
- 阻塞节点
- 合并节点
- 当前负责人

Task Map 可以用图视图，也必须提供紧凑列表模式，避免大任务图变成毛线团。

当前落地：

- 群聊消息支持多个任务胶囊。
- 群聊消息支持任务事件卡，用“任务分身术 / 任务合体 / 接力成功”等用户语言表达任务流。
- 项目右侧栏新增“地图”页签，优先读取服务端任务图，以紧凑卡片展示任务、依赖、负责人、状态和产出数量。
- 任务详情抽屉展示结构化时间线：任务动作、关联聊天、产出物和 proof 事件。
- 任务详情抽屉提供拆分、合并、改派、阻塞、恢复和取消操作。
- 合并和取消这类高影响操作会要求确认，避免 Agent 在群聊中一句话就改掉关键结构。

### Task Detail

任务详情页或抽屉：

- 当前状态
- 当前 owner
- 上下游依赖
- 阻塞原因
- 最近关键聊天
- 交接包
- 产物引用
- 可用操作

## 用户可见组件

### 任务胶囊

示例：

```text
#T12 A2A 群聊协作闭环
```

胶囊展示：

- 标题
- 状态颜色
- owner 头像或 emoji
- 阻塞标记

点击后打开 Task Detail。

### 任务事件卡

用于结构化动作：

- 任务已创建
- 任务已拆分
- 任务已认领
- 任务已交接
- 任务被阻塞
- 任务已恢复
- 任务请求评审
- 任务已合并
- 任务被重开

事件卡文案必须使用用户语言，不暴露 runtime、routing、worklist、chain 等内部词。

### 任务通知

用于“有人改了任务事实，相关角色应该知道”的轻量提示。

示例：

```text
任务通知 @toad @mario：TASK-006「代码评审」状态 in_review → done（来自 @peach）。这是任务事件通知，不会发起 A2A 交接。
```

显示规则：

- 作为系统消息出现在群聊中。
- 只解释任务变化和被通知角色。
- 不使用“团队规则阻止”“转交失败”等交接语义。
- 不要求 Agent 额外确认收到。
- 如果确实需要另一个 Agent 执行新动作，才由发起方使用 `@agent` 触发 A2A。

### 系统轻推

用于“下一位已经很明确，但没人主动启动”的最小唤醒。

示例：

```text
系统轻推 @toad：TASK-008「Execution Adapter」请继续处理。 这是 Wakeup 提醒，不是 A2A 交接。
```

触发条件：

- 任务为待处理且负责人明确，依赖已满足。
- 任务进入评审且评审角色明确。
- 上游依赖完成，下游待处理任务可以继续。

不触发条件：

- 没有负责人或没有评审人。
- 需要产品判断、破坏性操作或权限确认。
- 只是群聊里的普通提及。

### 当前态摘要

群聊顶部或侧栏显示：

- 当前进行中任务数
- 当前阻塞任务数
- 最近一次交接
- 下一步建议

示例：

```text
3 个任务进行中 · 1 个等待合并 · 1 个需要你确认
```

## 关键交互规则

- Agent 可以闲聊式表达，但改变任务状态必须产生结构化动作。
- 用户可随时打断、改派、暂停、合并或要求总结。
- 高影响操作需要确认：跨分支合并、取消任务、抢占他人正在执行的任务。
- 失败提示必须告诉用户下一步能做什么。
- 聊天不应该强迫用户读日志；日志和 proof 放在详情里。
- 任务状态同步走任务通知，跨 Agent 执行动作才走 A2A 交接，避免“只是更新状态却被交接规则拦截”。
- 聊天工作区进入可交互态后，后台状态刷新或配置重试不得卸载输入区；未发送草稿和当前焦点只能由用户操作或发送成功改变，不能被刷新流程隐式清除。刷新期间输入框保持可编辑，但发送动作暂缓，避免 Human Command 读取半更新的运行配置。该约束由 [#67](https://github.com/changhuaqiu/agent-task-team/issues/67) 跟踪。

## 已弃用的假设

- 不再把聊天文本本身视为任务状态来源。
- 不再依靠普通 `@agent` 提及改变任务 owner。
- 不再在接收方尚未开始执行时提前改派任务。

## 成功标准

- 用户能从群聊看懂谁在做什么。
- 用户能从任务图看懂任务如何拆分、等待和合并。
- 用户不需要理解内部执行概念，也能知道交接为什么失败。
- 多任务并行时，群聊仍可读，任务事实仍一致。
- 任何任务状态都能从任务详情追溯到对应聊天和结构化动作。
- 后台状态刷新期间输入框保持挂载，用户正在编辑的草稿和焦点不丢失。
