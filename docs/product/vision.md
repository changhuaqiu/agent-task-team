# Agent Task Hub 愿景

> **让 AI 从会写代码，进化到能负责交付。**

## 我们看到的变化

代码生成已经不再是 AI 软件开发的最大瓶颈。

真正困难的是：当任务跨越几十个步骤、多个 Agent、不同工具和数小时甚至数天时，系统能否一直记得目标，准确传递数据，在失败后继续工作，并用真实证据证明结果已经完成。

单次对话可以写出漂亮代码，却很难天然承担完整交付：

- 上下文会膨胀、稀释和漂移；
- Agent 会忘记前序状态，交接会丢失责任和关键事实；
- 模型擅长理解与判断，却不擅长长期保存状态和精确搬运数据；
- 进程、会话或外部服务失败后，聊天记录不能自动恢复工作；
- “Agent 说完成了”不等于代码通过评审、测试、验收并真正交付。

因此，下一阶段的竞争不只发生在模型层，而发生在模型周围的工作环境：上下文、任务、责任、能力、状态、证据、恢复和评估如何共同组成一个可靠闭环。

## 我们是什么

**Agent Task Hub 是面向软件交付的 Agent OS。**

如果把 Claude、Codex、OpenCode 等模型和执行引擎看作高性能 CPU，它们天然擅长理解、推理和生成，却不天然拥有可靠的内存管理、进程调度、持久状态、进程间通信、安全边界和故障恢复。

Agent Task Hub 补齐的正是这一层操作系统能力。它把不同模型、运行引擎、Skill 和工具组织成一支能够持续工作的 Agent 团队，并为软件交付提供统一的运行环境：

- 知道目标、验收标准、项目边界和授权；
- 获得当前任务真正需要的项目知识与 Skill；
- 通过任务图和明确交接保持责任连续；
- 在受控范围内修改代码、调用工具、评审和验证；
- 从持久化事实、工作目录和执行回执中恢复；
- 用评审、测试、Web UI 验收和外部结果证明交付；
- 通过可版本化知识、Skill 和评估结果持续变好。

其中，**Team Harness 是 Agent OS 的执行内核**：它负责让团队围绕一个目标持续完成“观察—规划—执行—评审—修复—交付”的循环。Agent OS 则在 Harness 之外进一步管理团队的完整运行环境和生命周期。

用户创建的不是“一组聊天窗口”，而是**一次交付**：

> 我说清楚要什么、怎样算完成、在哪个范围工作、允许系统做到哪一步；之后团队自己推进，直到带着证据交付，或只向我提出一个真正无法自行决定的问题。

## 核心产品命题

### 1. Agent 需要的不是容器，而是操作系统

更多 Agent、更多工具、更多上下文不会自然组成一支可靠团队。没有统一的状态、调度、通信和治理，它们只是一组同时运行的进程。

Agent Task Hub 像操作系统管理计算资源一样管理 Agent 团队：

| 操作系统职责 | Agent Task Hub 中的对应能力 |
|---|---|
| 进程与调度 | Task Graph、Dispatch、责任持有、自主交付 Supervisor |
| 内存管理 | 分层上下文、预算门禁、渐进加载、项目知识与 Skill |
| 文件系统与持久状态 | 项目工作区、Worktree、Session、任务事实与执行回执 |
| 进程间通信 | A2A 交接、交接包、团队日志与共享上下文 |
| 设备与能力管理 | ACP Runtime、Skill、MCP、Browser 与外部 Provider |
| 安全与权限 | 授权范围、Policy、幂等、租约、质量门禁 |
| 故障恢复 | Checkpoint、重试、Reconcile、Session Generation 与现场恢复 |
| 监控与演进 | Trace/Span、Proof、评估、版本实验与能力回流 |

因此，我们不是在一个聊天界面里“多放几个 Agent”，而是在构建一套让 Agent 可以被运行、协作、治理和持续进化的软件交付操作系统。

### 2. 从对话完成，转向目标交付

聊天是入口，不是产品的终点。

Agent Task Hub 的一等对象是带目标、验收标准、范围和授权的交付。任务拆解、Agent 调用、交接、评审、验证、PR 和恢复都是交付过程中的事实，不能用一段“已经完成”的回复代替。

### 3. 系统工程比更长的 Prompt 更重要

Prompt 可以告诉 Agent 应该怎么做，但不能单独保证它始终做到。

可靠性来自环境设计：需要的信息按需出现，合法行动清晰可见，精确数据由系统传递，重要状态可持久化，危险动作受授权约束，失败可以回退和继续。

我们的目标不是写出越来越长的提示词，而是让正确路径成为 Agent 最自然、最短的路径。

### 4. 让模型做判断，让系统守住确定性

Agent 负责开放式工作：理解目标、设计方案、拆解任务、实现、评审和修正。

系统负责确定性工作：状态保存、数据传递、权限、幂等、租约、责任转移、完成门禁和证据归档。

这不是限制 Agent，而是把它从不擅长的机械工作中释放出来，让推理能力用于真正需要判断的地方。

### 5. 人做决策，不做人工调度器

人始终是目标、品味、边界和最终责任的拥有者。

但人不应该反复提醒 Agent 下一步做什么，也不应该在多个窗口之间搬运上下文、重试进程或核对谁该接棒。正常路径中，用户只需要定义目标和验收；系统只有在缺少必要知识、授权不足或风险不可安全判断时才请求介入。

### 6. 证据高于自述

Agent 的文本回复是一种表达，不是完成事实。

交付必须能够回答：改了什么、谁评审过、运行了什么测试、每条验收标准由什么证据支持、外部动作是否真实发生、还存在哪些限制。没有结构化证据，就不能把“运行结束”展示为“交付完成”。

### 7. 团队成长必须可以验证

“领养一支团队”仍然是 Agent Task Hub 的情感表达，但团队成长不靠人格设定或聊天次数证明。

真正的养成发生在：项目规则被沉淀，Skill 被版本化，失败经验进入知识体系，RoleCard 和协作策略经过评估，候选变化在回归测试中证明没有退化。

团队不是因为使用更久而自动变强，而是因为经验被保存、能力被验证、变化被治理而持续进化。

## 产品边界

Agent Task Hub 当前聚焦于**软件交付 Agent OS**，而不是试图成为覆盖所有行业和业务流程的通用操作系统。

我们优先服务：

- 已经在使用 Coding Agent，但缺少长任务、多人协作和可靠收口能力的个人与团队；
- 希望把一个产品目标持续推进到代码、评审、测试和交付结果的创造者；
- 需要比较 Agent、RoleCard、Skill 和上下文策略实际效果的 Agent 工程团队。

我们不把以下方向作为核心：

- 另一个通用 AI 聊天界面；
- 以角色数量、人格互动或群聊热闹程度衡量价值；
- 让一个 Boss Agent 成为所有事实和完成判断的唯一权威；
- 用可视化工作流要求用户预先编排所有步骤；
- 让 AI 替代人的产品判断、风险决策和最终责任。

## 一句话承诺

> **一次说清目标和验收，Agent 团队持续推进，直到有证据地交付，或只向你提出最小必要问题。**

- **项目名称**：Agent Task Hub
- **产品类别**：面向软件交付的 Agent OS
- **执行内核**：支撑 Agent 团队持续循环的 Team Harness
- **核心主张**：让 AI 从会写代码，进化到能负责交付
- **用户承诺**：一次说清目标，持续自主推进，有证据地交付
