## 产品判断

默认团队不是一个普通示例，而是用户第一次理解 Agent Task Hub 的样板团队。它必须回答一个朴素问题：

> 这六个人分别处在哪个交付阶段，怎么进入门禁，失败后打回谁，什么时候升级？

如果默认团队只展示六个头像，却只有三个人进入主流程，用户会把 TeamPack 理解成角色陈列，而不是可运行的协作团队。

默认团队应参考 Harness 的思想：不是让六个人机械串行，而是用阶段、并行 lane、审批门禁、打回回路和升级路径组织交付。

## 核心对象

默认团队由六个用户可理解的角色组成：

| 角色 | 用户称呼 | 用户理解 |
| --- | --- | --- |
| Mario | 项目统筹 | 把目标变成任务，协调节奏，处理阻塞 |
| DK | 架构工程 | 在高风险技术点前做架构判断 |
| Luigi | 前端实现 | 负责页面、交互和客户端集成 |
| Toad | 后端开发 | 负责接口、数据模型和服务端逻辑 |
| Peach | 代码评审 | 检查质量、安全、可维护性和测试风险 |
| Yoshi | QA 测试 | 验证行为、回归和最终交付质量 |

## 协作样板

默认 6 人组采用 Workflow Harness 模式：

1. `planning`：Mario 接收目标，拆成任务，分派前端/后端 lane，定义验收口径。
2. `implementing`：Luigi 和 Toad 按任务域并行执行，可直接对齐接口和交互边界。
3. `review_gate`：Peach 做代码评审；DK 只在架构、数据模型、性能、安全、跨模块边界等高风险点上场。
4. `test_gate`：Yoshi 做集成测试、规格一致性和交付完整性验证。
5. `done`：门禁通过后结束；若失败，直接打回责任角色。

这个样板以后可以推广到其他 TeamPack：先定义阶段，再定义每个阶段的 owner、入口条件、出口条件、reject 目标、升级条件和证据要求。

## 门禁回传规则

评审门禁需要一条独立于 A2A 链的回传线：

- 实现者提交 `in_review` 时，系统轻推评审角色开始审查。
- Peach 或 DK 这类评审角色给出结论后，系统轻推 Mario 确认评审结论。
- 如果评审结论是通过，系统同时轻推 Yoshi 进入测试门禁；这不是 Peach 必须在线发出的聊天交接，而是 review_gate 的正式出口。
- 这条回传是任务门禁控制，不是普通 A2A 交接；即使 Mario 已经出现在当前 A2A 链中，也不能被“重复唤醒”拦截。
- Mario 确认通过后，系统再解锁下游依赖任务；若不通过，则由评审角色直接打回责任实现者，必要时升级给 Mario。

## 阻断升级规则

如果某个 agent 的直接转交被协作规则阻止，流程不能停在“无待办任务”：

- 能直接走通的路径继续直接转交，例如 Peach 到 Yoshi 的测试交接。
- 运行态仍带旧协作矩阵的默认团队，需要兼容到当前 Harness 路径，避免旧项目继续挡住正式门禁出口。
- 如果直接转交仍被阻止，系统应把原始请求和阻断原因升级给可达的统筹角色，通常是 Mario。
- 这种升级是为了解决阻塞，不是礼貌性确认，也不是状态广播。

## 人格自治闭环

默认团队的自治主要依赖角色人格，而不是后台把每一步机械推下去：

- Mario 的人格负责“我是否真的把团队启动起来”，不是只写调度话术。
- Luigi/Toad 的人格负责“我是否把可评审证据补齐”，不是只说代码已完成。
- Peach/DK 的人格负责“我是否把门禁结论传到下一步或打回责任人”，不是只写评审意见。
- Yoshi 的人格负责“我是否验证到可交付边界”，不是只在临时环境看一次结果。

因此每个角色结束一轮时必须留下闭环：

- 更新任务状态并提交证据。
- 或创建真实派发，并确认有派发回执。
- 或创建 blocker 并升级给可达统筹。
- 或说明具体外部等待条件和恢复负责人。

文本调度不是执行事实。比如“@luigi 请做 TASK-002”或“两条管道已启动”只有在系统产生对应的 dispatch receipt、A2A pass offer、task wakeup dispatch 或执行启动回执后，才算真的启动。

并行管道必须按 `n/n dispatched` 口径确认；如果只启动了一部分，角色应重试或升级，而不是宣布全部开工。

## 可执行交付门禁

默认团队不再把“运行结束”或“看板标记”当成交付完成：

- Luigi/Toad 进入评审前必须提交 `implementation_evidence`，包含适用的 install、build、test 和影响边界说明。
- Peach/DK 如果发现实现证据缺失，必须退回补证据，不能只凭代码阅读通过。
- Yoshi 验收通过后只能进入 merge-ready，不能直接代表最终 done。
- Mario 只有在完成主分支或目标集成分支验证后，才能提交 `delivery_evidence` 并标记 done。
- 如果状态流转缺证据，系统应拒绝流转并记录缺少的字段；CLI 成功退出只说明进程结束，不自动进入 review。

## 不做范围

- 不把默认团队包装成所有任务都必须六人全量参与。
- 不让用户理解内部运行时、路由、矩阵、会话等实现概念。
- 不用普通聊天文本改变任务事实；任务状态仍由 Task Graph 和结构化动作维护。
- 不把系统守护器变成中央决策者；系统只兜底派发回执、证据、阻塞和超时这些事实，专业判断仍由角色人格承担。
- 不把 Mario 放在每次交接中间；只有边界不清、反复失败、需要取舍时才升级给 Mario。

## 成功标准

- 用户看一眼团队就知道每个角色为什么存在。
- 实现、评审、QA 不再混成同一个模糊“完成”阶段。
- 前后端可以直接协作，不必所有细节都绕回统筹。
- 架构、评审、QA 是清楚的质量门禁，而不是旁路顾问。
- review/test 失败可以直接打回责任人，而不是先绕 Mario。
- agent 可以靠人格和职责自驱推进；只有缺回执、缺证据、阻塞或超时时才需要系统轻推责任角色回来。
- 这个 6 人组可以成为后续 TeamPack 设计的模板。
