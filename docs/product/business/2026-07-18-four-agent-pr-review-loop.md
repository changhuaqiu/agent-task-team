# 四角色工程交付协作模型

> 状态：基础闭环已实现，真实合并演练中

## 用户问题

当前四角色团队已经能分派、实现和唤醒质量门禁，但用户仍无法确认“开发是否真的提交了可评审代码”“评审是否真的发生在 PR 上”。聊天中的一句“已提交/已通过”不应成为工程事实。

## 产品决策

默认团队以工程交付物而非角色自述推进：Mario 管目标和闭环，DK 管架构风险，Luigi 交付 PR，Peach 在 PR 上留下真实评审并测试。平台把 provider 回执转成聊天卡片，让用户在对话流中直接看到交付对象、评审结论和下一步。

主流程只有一个：完成当前 task 的可合并交付。PR、评审、测试和合并是同一 task 的连续证据，不拆成互不关联的聊天消息。

## 用户可见对象

- **开发交付卡**：Luigi 提交了什么、在哪个 PR、对应哪个 commit、验证了什么；
- **代码评审卡**：Peach 对哪个 commit 做了什么结论、真实评论在哪里、需要谁处理；
- **合并闭环卡**：什么已进入 main、main 上验证了什么、是否还有风险。

内部的 dispatch、runtime、receipt、proof 等术语不进入主卡片文案。

## 角色关系

- Mario 不兼任实现者或审批者；
- DK 是按风险触发的架构 gate，不是每个 task 的固定中转；
- Luigi 对实现和 PR 完整性负责；
- Peach 是唯一默认质量 gate owner，负责代码评审与集成测试；
- 一个交付只允许存在一张权威 Task Graph。共享工作目录中的 `TASKS.md` 是当前会话的兼容投影，不能把旧会话任务再次导入为“影子任务”；
- 角色是否参与由当前 WorkContract / QualityGate 决定，而不是因为角色出现在团队列表或聊天里。Mario、Luigi、Peach、DK 没有当前责任时保持静默；
- 评审结论必须绑定被评审 Task 的精确 revision。进入 WorkContract 后，文件投影不能把 `in_review`、`blocked` 或其他权威状态改回执行态，避免实现者和评审者在同一份成果上重复接力；
- 用户默认保留 merge 权限，后续可以显式授予团队协调者。

当 PR 新增提交时，聊天不会覆盖旧评审，而是明确显示“需要重审”；只有当前版本零 blocker 的真实评审、授权合并和 main 复验都完成后，Mario 才能发布合并闭环卡并关闭任务。

GitHub 的“已评论”和团队的“质量通过”是两个不同事实：前者证明真实外部评论存在，后者由已绑定的 Peach 运行实例明确给出。普通评论默认只记证据，不自动获得合并放行权。

## 成功标准

用户无需阅读终端日志，就能在聊天中回答：谁在负责、代码在哪、评审针对哪个版本、真实评论在哪、为什么被打回、何时进入 main。
