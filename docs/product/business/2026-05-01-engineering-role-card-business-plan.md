# 工程型角色卡机制业务文档

## 一、文档目的

本文档用于定义 Agent Task Hub 中“工程型角色卡机制”的业务目标、用户价值、核心对象、使用场景与落地路线。

这里讨论的不是娱乐型角色扮演，也不是陪伴式人格设定，而是面向软件研发协作的 **工程岗位型角色卡**：

- 谁负责什么
- 谁不负责什么
- 谁应该用什么方式工作
- 谁的输出应该长什么样
- 谁在什么情况下必须升级、交接或请求确认

目标是让多 Agent 协作从“多个 CLI 能跑”升级成“多个工程角色可协同、可追踪、可治理”。

---

## 二、为什么要做

### 1. 当前问题不是 Agent 不够多，而是角色边界不清

现阶段系统已经在逐步具备：

- 多 CLI 运行能力
- 多任务协作
- 对话、任务、执行链路

但一个关键问题仍然存在：

**系统知道“能跑谁”，但还不知道“该让谁做什么、以什么标准做、做到什么程度算完成”。**

这会带来几个典型问题：

- 相同问题在不同 Agent 上表现不稳定
- 用户无法形成“这个角色适合干什么”的清晰心智
- 任务分派依赖临场判断，缺乏稳定规则
- 评审、实现、规划等岗位容易互相越界
- 系统只能管理“执行”，很难管理“协作”

### 2. 多 Agent 产品真正需要的是岗位协作，不只是模型切换

用户最终不关心底层是 `OpenCode / Claude / Codex`，而关心：

- 谁是规划师
- 谁是前端实现
- 谁是评审
- 谁是架构守卫
- 谁可以直接改，谁只能提出意见

如果没有角色卡，系统就只能停留在“模型切换器”阶段。

如果有了角色卡，系统才可能真正演进为“工程协作系统”。

### 3. 角色卡是连接“人设”、“能力”和“流程”的中间层

角色卡机制的意义，不是做一个漂亮头像或名字，而是把以下内容收敛到一个统一对象里：

- 角色身份
- 职责边界
- 工作方式
- 允许使用的能力
- 输出格式
- 质量门槛
- 升级机制

它是产品从“多 CLI 管理”向“多角色协作治理”升级的关键中间层。

---

## 三、产品定位

### 定位一句话

工程型角色卡机制，是 Agent Task Hub 中用于定义、绑定、调度和治理工程协作角色的基础能力层。

### 角色卡不是这些东西

- 不是聊天陪伴人设
- 不是单纯的 prompt 模板
- 不是模型别名
- 不是账号配置页的附属字段

### 角色卡是这些东西

- 是岗位定义
- 是协作规则
- 是任务路由依据
- 是输出质量约束
- 是运行时行为边界

---

## 四、目标用户

### 1. 独立开发者 / 小团队负责人

他们最需要的不是“更多模型”，而是：

- 让多个 Agent 各司其职
- 避免一个 Agent 既规划又实现又评审
- 在项目中形成稳定工作流

### 2. 高频使用多 Agent 的高级用户

他们已经知道不同模型有不同风格，但缺少一个稳定机制来把这些风格沉淀为“岗位”。

### 3. 后续可扩展用户

- AI 项目经理
- 研发负责人
- 设计协作用户
- 需要长期维护 Agent 团队配置的用户

---

## 五、核心业务价值

### 1. 让用户从“选模型”转向“选角色”

这是心智升级的关键。

用户不需要每次都想：

- 这次用 Claude 还是 Codex？

而应该想：

- 这次交给“架构评审”还是“前端实现”？

### 2. 让任务分派可解释

如果系统把某项工作交给某个角色，用户可以清楚看到：

- 为什么是它
- 它的职责是什么
- 它的边界是什么
- 它输出应满足哪些要求

### 3. 让协作行为可治理

角色卡能定义：

- 哪些角色能直接改代码
- 哪些角色只能提出建议
- 哪些角色必须附证据
- 哪些角色必须经过用户确认

工程实现类角色必须能直接改代码，否则多 Agent 协作会退化为“顾问链”。例如“前端实现”“后端开发”“实现者”属于执行岗位，应允许修改代码、创建文件，并在高风险操作（如数据库 schema 变更、公共接口删除）时要求确认；“代码评审”“架构评审”“质量守卫”才默认是建议/评审岗位。

这直接提升系统稳定性与可控性。

### 4. 让能力与人格都能沉淀为资产

一旦角色卡成为独立对象，它就不再是一次性的 prompt，而是可复用、可迭代、可分享、可治理的资产。

---

## 六、角色卡解决的业务问题

### 问题 1：角色边界模糊

表现：

- 规划师直接去实现
- 实现者擅自调整需求
- 评审者开始写大量代码

角色卡的解决方式：

- 显式声明职责
- 显式声明非目标
- 定义必须升级或交接的条件

### 问题 2：分派逻辑不稳定

表现：

- 同样的任务有时给 A，有时给 B
- 用户不理解系统路由逻辑

角色卡的解决方式：

- 为任务类型绑定角色
- 为角色绑定默认能力与工作风格
- 让“路由”从临场判断变成规则

### 问题 3：输出不一致

表现：

- 有的角色说大段空话
- 有的角色不带证据
- 有的角色没有结构化交付

角色卡的解决方式：

- 定义输出规范
- 定义证据要求
- 定义质量门槛

### 问题 4：系统难以形成长期组织记忆

表现：

- 换一个模型就像换一个人
- 系统无法积累“这个角色应该怎么做事”

角色卡的解决方式：

- 把角色定义从运行时抽离出来
- 让角色和模型/runtime 解耦
- 让角色成为长期存在的组织对象

---

## 七、角色卡的核心业务对象

从业务角度看，一张工程型角色卡至少应包含以下信息：

### 1. 角色身份

- 名称
- 显示名
- 简介
- 标签
- 适用场景

### 2. 职责定义

- 主责
- 非职责
- 成功标准

### 3. 工作方式

- 是否先澄清再执行
- 是否优先评审再实现
- 是否默认结构化输出
- 是否偏简洁或偏详细

### 4. 行动边界

- 哪些变更必须问用户
- 哪些情况必须升级
- 哪些操作不允许执行

### 5. 能力绑定

- 可连接的账号或执行方式
- 可使用的工具
- 可使用的 skill
- 偏好的执行环境

### 6. 输出与质量约束

- 输出形式
- 是否必须带文件引用
- 是否必须附证据
- 是否必须给风险分级

### 7. 人格（Persona）

- 角色独白式自我介绍（首次唤醒时注入 prompt，锚定 session 风格）
- 语气风格
- 思维模式
- 行为习惯
- 协作方式

---

## 八、当前落地的用户心智

当前实现已经把角色卡从“单个 agent 的 prompt 配置”推进到“团队成员身份资产”：

- 用户看到的是角色和团队，而不是底层执行管道。
- RoleCard 定义一个角色应该怎么工作、有什么边界、需要哪些能力。
- TeamPack 把多个角色组合成一个团队，并定义任务流程与团队协作规则。
- 项目绑定 TeamPack 后，页面、派发、提示词、Skill 绑定和 A2A 都应围绕这支团队展开。
- 账号与执行方式是角色能否被派发的条件，但不是用户理解团队的主入口。

### 马里奥（统筹/Coordinator）的岗位闭环

马里奥收到项目目标后，首要职责不是亲自实现，也不是只在聊天里描述“建议谁来做”，而是建立可执行、可追踪的工作结构：

- 读取目标、验收标准、当前 Task Graph 与可用团队成员；
- 将未分配的根任务纳入同一份 Task Graph proposal，必要时拆成边界清楚的子任务和依赖；
- 为每个可执行任务指定符合职责的项目成员，并补齐必要的评审、验证或汇总节点；
- proposal 被平台接受后，由系统提交任务图并自动派发已就绪任务；马里奥继续跟踪阻塞、重规划、门禁和最终收口；
- 只有存在无法从项目事实推断的关键选择时才请求用户决策，不能用叙述性计划、聊天 @ 或直接转交替代任务图。

这项约束既体现在默认角色卡中，也由每次 planning Invocation 的 WorkContract 和 Outcome owner 强制执行，因此新旧项目使用默认马里奥配置都能获得一致行为；用户明确自定义的角色指令仍被保留。

产品表达应避免把内部实现词放到主路径。面向用户时优先使用：

- “团队成员”
- “连接账号”
- “协作规则”
- “任务流程”
- “交给这个角色”

不应在主体验里优先暴露：

- `runtime`
- `channel`
- `routing`
- `bridge`
- `providerHints`
- `session`

这些词可以留在开发者文档或调试视图中，但不应成为普通用户配置团队时的第一层概念。

## 九、典型角色示例

### 1. 规划师

职责：

- 拆任务
- 排优先级
- 梳理依赖

不负责：

- 直接承担大规模实现

### 2. 前端实现

职责：

- 页面开发
- 状态管理
- 交互落地

不负责：

- 擅自重定义产品结构

可执行动作：

- 直接修改前端代码
- 创建必要组件与测试文件

### 3. 后端开发

职责：

- API 开发
- 数据模型设计
- 服务端逻辑实现
- 性能与可靠性优化

不负责：

- 擅自重定义产品需求
- 替代评审者批准自己的高风险改动

可执行动作：

- 直接修改后端代码
- 创建必要迁移、Repository、API 与测试文件
- 数据库 schema 变更、删除 API 端点等高风险操作需确认

### 4. 架构评审

职责：

- 边界判断
- 风险识别
- 替代方案建议

不负责：

- 在没有确认前改动关键架构

### 5. 代码评审

职责：

- 找回归
- 找隐患
- 评估测试覆盖

不负责：

- 替代实现者完成主要开发

### 6. 质量守卫

职责：

- 检查规范一致性
- 检查交付质量
- 检查流程完整性

不负责：

- 直接推进需求方向

## 十、角色卡与现有系统的关系

### 当前系统已经有的东西

- Project / Conversation
- Task
- Agent roster
- Runtime / CLI 能力
- 执行链路

### 角色卡要补上的东西

- 角色层
- 协作规则层
- 输出规范层
- 质量门槛层

### 关系图（业务视角）

```text
用户
  ↓
项目 / 会话
  ↓
任务
  ↓
角色卡（定义谁来做、怎么做）
  ↓
Agent 实例（运行时执行者）
  ↓
Runtime / CLI（底层执行能力）
```

关键原则：

- 角色卡不等于模型
- 角色卡不等于账号
- 角色卡不等于 runtime
- 角色卡是“谁来以什么方式工作”的定义层

---

## 十一、推荐的产品形态

### 1. 第一阶段：只做“预置角色卡 + 绑定”

先不做复杂编辑器。

第一阶段只需要：

- 提供系统预置角色卡
- 在 Agent 身上绑定角色卡
- 在任务分派时使用角色卡
- 在输出中体现角色卡约束

### 2. 第二阶段：支持工作区级自定义角色卡

允许用户：

- 新建角色卡
- 克隆系统角色卡
- 调整职责、边界、输出风格

### 3. 第三阶段：支持角色卡评估与演化

包括：

- 角色卡效果评估
- 角色卡版本管理
- 角色卡回滚
- 角色卡推荐与市场

---

## 十二、角色卡页面的业务要求

如果未来做角色卡管理页面，建议遵循以下原则：

### 页面目标

不是让用户编辑大量 prompt，而是让用户理解：

- 这个角色是干什么的
- 适合什么任务
- 不能干什么
- 当前绑定了哪个 agent

### 页面形态

建议采用：

- 角色卡列表
- 卡片摘要
- 详情页 / 抽屉
- 克隆与编辑

避免：

- 超长大表单
- 把底层实现字段直接暴露给用户

---

## 十三、分阶段业务路线

### Phase 1：岗位化

目标：

- 系统有明确岗位角色
- 用户可以理解不同 Agent 的职责

交付：

- 预置角色卡
- Agent 绑定角色卡
- 任务路由按角色进行

### Phase 2：可配置

目标：

- 用户可修改角色行为

交付：

- 角色卡详情
- 角色卡编辑
- 工作区级自定义角色

### Phase 3：可治理

目标：

- 角色卡成为组织资产

交付：

- 版本管理
- 质量评估
- 演化记录
- 推荐/模板体系

---

## 十四、成功标准

如果角色卡机制做对了，用户应该能明显感受到：

### 1. 能快速理解谁该做什么

用户不再先想“该用哪个模型”，而是先想“该用哪个角色”。

### 2. 系统分派更稳定

同类任务会由相近角色处理，输出风格更一致。

### 3. 协作更像团队

角色之间有边界、有交接、有质量要求，而不是多个 Agent 混在一起抢活。

### 4. 长期可积累

角色卡不再是一次性的 prompt，而是可以持续迭代的组织能力。

---

## 十五、结论

工程型角色卡机制，不是一个可有可无的装饰功能，而是多 Agent 协作系统迈向“可治理工程团队”的关键基础设施。

它的本质价值在于：

- 把 Agent 从“可执行工具”提升为“岗位协作者”
- 把协作从“临场发挥”升级为“规则驱动”
- 把 prompt 从“隐式经验”升级为“显式资产”

对于 Agent Task Hub 来说，角色卡机制将成为连接以下几层的核心中间层：

- 用户任务意图
- 项目协作流程
- Agent 组织结构
- Runtime 执行能力

从业务角度看，这是一个值得尽快立项的中间层能力。
