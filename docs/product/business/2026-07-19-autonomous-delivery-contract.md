# 自主交付产品契约

**日期**：2026-07-19
**状态**：Accepted

## 用户心智

用户创建的不是“一个聊天”，而是“一次交付”：

> 我说清楚要什么、如何算完成、允许系统做到哪一步；之后系统自己推进，我只看最终结果或处理真正的例外。

产品背后的核心不是“替用户拉起几个 Agent”，而是给 Agent 团队一个可以持续工作的环境：它知道项目和团队当前发生了什么，知道有哪些合法行动，能看到行动后的真实反馈，也能在成员或进程失败后从原事实继续。因此用户面对的是一个有交付能力的团队，而不是一组需要人工逐个提醒的聊天窗口。

## 创建交付时只问四类信息

1. **交付目标**：要得到什么结果。
2. **验收标准**：怎样证明结果可用。
3. **工作范围**：在哪个项目/仓库内工作。
4. **交付授权**：是否允许改代码、推送、创建 PR、自动合并。

默认值应减少配置负担：

- 允许在所选工作区改代码；
- 要求 Review、构建/测试和 Web UI 端到端验证；
- 允许创建 PR；
- 自动合并默认关闭，用户明确开启后才执行。

自主交付要求选择具体项目目录。没有可定位的工作区，就无法安全注入项目上下文、
限制文件证据范围或执行真实 Web UI 端到端验收，因此创建阶段直接失败关闭。

## 运行中

创建自主交付时，团队配置加载只负责让成员可用；同一次创建只能启动一条交付规划链，
不能再额外发起普通聊天式方案讨论，也不能要求用户二次确认后才开始拆解任务。

主视图只展示：

- 当前阶段；
- 已完成的验收项；
- 正在处理的工作；
- 是否存在需要用户决策的异常。

Agent 间聊天、session、runtime、receipt、lease 等进入调试视图，不进入主任务体验。

## 异常

系统不能只说“失败，请重试”。异常卡片必须包含：

- 卡在哪里；
- 系统已尝试的恢复；
- 需要用户选择的最小问题；
- 选择后会如何继续。

若无需用户知识或授权即可安全恢复，不产生异常卡片。

## 最终交付

最终只展示一个 `DeliveryBundle`：

- 交付摘要；
- 验收标准逐项结果；
- 每条验收标准对应的可追溯证据；
- 关键变更；
- Review/测试/Web UI E2E 的验证方式、工具、报告与用例；
- PR、commit、合并或部署链接；
- 已知限制和后续建议。

主界面使用“验收证据、验证报告、测试用例”等用户语言。内部 `Receipt`、`Proof`、
`Envelope` 等标识只保留在调试视图；没有结构化验收回执时，页面不得展示“交付完成”。

## 成功指标

- 正常路径用户消息数：1。
- 中间人工路由次数：0。
- 可自动恢复故障的人工介入率：0。
- 重复 Provider 副作用：0。
- “显示完成但未满足验收”的次数：0。
